## Proposed architecture

1. **Mount one embedded BQQuiz feature.** Keep BQSearch's lazy Quizzes entry. The bridge resolves the catalog and storage, then supplies a verified catalog, a quiz repository, a Scripture provider and a host exit callback to the original V5 controller. The controller retains transitions among Library, Question Bank, Generator and Practice. Keep the advanced install control as a host capability outside the standard BQQuiz workflow.
2. **Scope the styles at the quiz boundary.** Give the original frame and Practice branch the same scoping root. Preserve the original cascade, selector specificity and media queries. Translate global `:root`, `html`, `body`, `#root`, generic class names and dark-theme selectors to that root. Use host-scoped print visibility during original Practice printing so Lookup chrome is hidden in that print view only. Keep document-level theme and CSS variables under BQSearch ownership.
3. **Share Scripture through the existing provider.** Adapt the original `getVerse(reference)` contract to BQSearch's `createPackScriptureProvider`. Resolve against the active pack and division. Proposed drawer behavior is to use the pack's division coverage and show reasons when verse text is unavailable, without changing the original Generator's question-derived coverage or changing Lookup settings. Decide during approval whether the drawer should also honor the narrower Lookup study-range selection. Retain range resolution and unavailable behavior in either case.
4. **Keep published data immutable and local data separate.** Keep the existing approved JSON, canonical digest and Workbox precache, plus merge precedence and manual catalog installs. Use original models at the screen boundary. Preserve optional publisher, reference, revision and provenance fields and any extensions on existing user records. Keep the bundled and manual catalog assets independent of practice persistence.
5. **Keep the existing database, with read adapters.** Use `bqquiz-local` v3 on the current origin and retain every store, key and index. The storage facade reads original and BQSearch quiz/preset shapes, preserves extra fields on writes, and opens already saved question IDs. It can resolve BQSearch's study-number preset metadata against its original context without forcing the original Generator to use current Lookup settings. Prefer no schema bump. Any migration that turns out to be necessary requires an idempotent path, rollback compatibility and a checkpoint before enabling it.
6. **Keep default workflows faithful.** Use the current original screens as acceptance evidence. Make only the four integration seams above necessary for embedding. Settings or workflow additions that exist only in the current integration can be considered independently. No replacement of Lookup, no coupling to Scorekeeper, no second service worker and no production changes.

## Data and functional risks

| Risk | Evidence and mitigation |
| --- | --- |
| **Same database name across different origins** | IndexedDB is origin/profile-scoped, and GitHub Pages path differences on one host do not create a new IndexedDB origin. Audit the exact original and preview origins separately. Same-origin BQSearch records should work directly. Cross-origin BQQuiz data needs an explicit transfer from the profile at its original origin. Never clear either database as an upgrade step. |
| **An existing export is not necessarily a full restore** | Original Bank exports two stores. Current BQSearch export includes all five and its visible import path only commits two. `migration.ts` has a commit helper, but its dependency checks treat only user questions and custom quizzes as valid targets. A real export can reference bundled questions and published quiz IDs, and session attempts and state maps also contain question IDs. Validate these relationships against user and published data before using it. Revisit remap completeness, transaction-time conflict handling, and repeated imports. Preserve local backups separately from the public catalog. |
| **Saved quiz or preset changes meaning** | BQSearch presets carry study numbers and pack/season/division/catalog context. Original presets carry canonical reference boundaries. BQSearch and original seeds may yield different selections. Stored question order, IDs, source revisions, seeds and filters need to survive unchanged. Resolve saved question IDs from exact data, and expose a missing-ID state instead of replacing questions. |
| **Current original Practice contains edge cases** | V5 assembles the sheet by filtering the global pool, which can reorder generated quiz IDs. Activity uses original question numbers for anchors, which can repeat across collections. Current update/remove helpers change attempts without recomputing derived session states. Reset creates a newer session, review printing did not show the slash in the audit, and the current Regenerate handler calls selection before the new seed takes effect. Record those findings as source behavior. Decide explicitly which, if any, to fix after parity is established. |
| **Catalog and user IDs collide** | The preview already combines bundled and local published catalogs by collection and record IDs. Original V5 also receives user records in the same visible arrays and tests ownership by ID. Check collisions before edits/imports so a published record cannot be mutated or a user's saved reference silently rebound. Preserve old records even when the visible catalog picks one canonical ID. |
| **Data written by concurrent tabs or autosave can race** | Practice autosave and management actions share a database with imports. Keep transaction-aware writes, commit before reporting success, prevent overwrite-on-conflict by default, and verify a second open tab and a refresh during a save. Preserve existing data across flag toggles and preview rollbacks. |
| **Shared CSS, print and worker ownership can regress host tools** | Original selectors such as `.app-header`, `.quiz-row`, `.generator-layout`, `body` and theme rules can apply beyond the feature if imported globally. Verify host screenshots, interactions and print routing with Quizzes enabled and disabled. Keep only the existing host service worker and check offline first open after precache. |
| **Browser and test gaps** | The comparison used Chromium viewports. Native Safari datalist, printing and touch, offline behavior of the proposed merged build and every original mutation edge case remain acceptance tests. The original committed browser spec still targets earlier inline controls and selector names. Update its expectations against V5 as part of verification, before relying on it as a parity gate. |

## Approval points

- Use the active V5 screens as the baseline, including the original Library layout for Saved Quizzes and the original Generator defaults. Decide whether integration-only controls should remain accessible separately.
- Choose whether the Practice reference drawer follows full division coverage or the currently selected Lookup study range.
- Decide whether a full five-store transfer from the standalone origin is needed for the first preview. The existing two-store export/import path suffices for collections and questions only.
- Review and approve any fixes to original behavior separately from the port so visual and functional differences have a clear reason.

No implementation, branch, deployment, or original-project files were changed during this audit.
